1.0 — THE LOOP IN ONE BREATH
--------------------------------------------------------------------------------

Today (request.md 8.3): Dream meets "beach", finds nothing in
thematic-memory, halts, files a ticket, dies. The Apprentice Protocol
replaces the halt with a DIALOG:

  Dream hits an unknown -> pauses THAT ASPECT of generation (never the
  whole run) -> emits a TeachRequest (precise questions + everything
  Dream already measured) -> a teacher (human at CLI, offline prompt
  packet, or API mode) answers with a RecipeResponse (declarative JSON
  recipe) -> Dream validates, sandboxes, tactically verifies, registers
  the knowledge permanently -> generation RESUMES using the new asset
  -> outcomes feed back into the asset's confidence record.

THE APPRENTICE'S CREED: never ask what you can measure. Dream measures
space, headroom, tier, anchors, distance, score. Dream asks only for
WORLD KNOWLEDGE: what things ARE, how they're BUILT, what they MEAN
tactically. Every question ships with the measurements attached so the
teacher answers once, precisely.

--------------------------------------------------------------------------------

JSON

    "schema": "dream-teach/1.0",
    "ticketId": "T-20260914-007",
    "trigger": {
      "kind": "asset_gap",              // asset_gap | theme_gap |
                                        // repair_deadlock
      "assetId": "palm_tree",
      "theme": "beach",

        "tier": 0,                      // attached to every question

        "footprintAvailable": [6, 6],   // meters

        "geometryBudgetLeft": 140

    },
    "questions": [ /* see 1.2 — always this order, only unanswered */ ],

  }

1.2 — THE SIX CANONICAL QUESTIONS (asked only when unanswerable)
--------------------------------------------------------------------------------

  Q1 SCALE — "What is this in the notebook universe?"
    expects: { realHeightM, doodleHeightM, colossal: bool, footprintM }
    (Dream converts to engine scale; the 1.8m character is the ruler.)

  Q2 TACTICAL ROLE — "What does it DO in a fight?"
    expects: one or more of [waist_cover, full_cover,
    traversable_catwalk, interior_corridor, landmark_anchor,
    grapple_anchor, hazard, pure_decor]
    (Roles drive BP3's colossal transform — scale BY FUNCTION.)

  Q3 COMPOSITION — "How is it BUILT from primitives?"
    expects: a RecipeResponse (1.3). This is the big one.

  Q4 INK HIERARCHY — "Which of the five inks, where?"
    expects: per-part ink assignment from the semantic palette (LAW 2).

  Q5 COLLISION & CLEARANCE — "What is solid? What is walkable?"
    expects: { solidParts, walkableParts, clearanceM, headroomM,
    noCollideSub03mParts } — the NAV CONTRACT (LAW 5).

  Q6 VARIATION — "How does it VARY in nature?"
    expects: parametric ranges (height/lean/girth spreads) so
    instantiation (1.4) kills the Static Clone Problem for this asset
    forever.

  PARTIAL ANSWERS ARE FINE. A teacher may answer Q1-Q2 and let Dream
  synthesize Q3 from a known cousin asset ("palm_tree ~ trunk+crown
  like buildPineTree, but lean heavy") — the request marks inferred
  fields and lowers the confidence score accordingly.

1.3 — THE RecipeResponse GRAMMAR (dream-recipe/1.0)
--------------------------------------------------------------------------------

A recipe is a DECLARATIVE PARAMETRIC PART TREE. JSON only; no code;
no eval (LAW 7). Composite hierarchies come from THREE constructs:
parameters, expressions (whitelisted, 1.3b), and foreach replication.

JSON

  {
    "schema": "dream-recipe/1.0",
    "id": "palm_tree",
    "version": 1,
    "provenance": { "teacher": "field_guide", "date": "2026-09-14" },
    "params": {
      "height":     { "min": 14, "max": 22, "default": 18 },
      "leanDeg":    { "min": -12, "max": 12, "default": 4 },
      "trunkR":     { "min": 0.45, "max": 0.7, "default": 0.55 },
      "fronds":     { "min": 6, "max": 10, "default": 8 }
    },
    "parts": [
      { "id": "trunk",
        "prim": "cyl",
        "args": [0, 0, 0, "@trunkR", "@height"],
        "opts": { "ink": "BK", "seg": 8, "jitter": { "amp": 0.08 } },
        "tilt": { "axis": "z", "deg": "@leanDeg" } },

      { "id": "crown_hub",
        "prim": "sphere",
        "args": ["0", "@height", "0", "0.5"],
        "opts": { "ink": "GR", "noCollide": true } },

      { "id": "frond",
        "foreach": { "var": "i", "from": 0, "to": "@fronds - 1" },
        "prim": "wedge",
        "args": [ "cos(i * 360 / @fronds) * 1.6",
                  "@height - 0.4",
                  "sin(i * 360 / @fronds) * 1.6",
                  "2.8", "0.35", "1.2" ],
        "opts": { "ink": "GR", "noCollide": true },
        "rotateY": "i * 360 / @fronds" }
    ],
    "anchors": {
      "grapple_top":    [0, "@height + 7", 0],
      "coconut_cluster": [0, "@height - 1.2", 0]
    },
    "tactical": {
      "roles": ["landmark_anchor", "grapple_anchor"],
      "climbRoute": null,
      "coverValue": null
    },
    "tests": { "selfClearance": 0.3, "grounded": true }
  }

  SCHEMA RULES (all enforced at L1 validation):
    - prims: ONLY the builder's registered set (incl. BP4 organics)
    - args/opts: numbers, strings, or whitelisted expressions
    - tilt/rotate: single-axis degrees, expressionable
    - foreach: bounded replication (max 24 iterations — a hard guard
      against recipe bombs)
    - budgets: total parts <= 40, estimated geometry calls <= 60
      (over-budget recipes fail L1 with a line-level report)

1.3b — THE WHITELISTED EXPRESSION ENGINE (how this avoids eval)
--------------------------------------------------------------------------------

  Expressions like "cos(i * 360 / @fronds) * 1.6" are parsed by a
  ~100-line recursive-descent parser whose grammar is FROZEN:

    expr    := term (('+' | '-') term)*
    term    := factor (('*' | '/' | '%') factor)*
    factor  := number | '@'param | var | func '(' expr (',' expr)* ')'
    func    := sin | cos | sqrt | abs | min | max | round | floor | clamp
    var     := foreach variables only

  Anything outside the grammar — property access, function calls by
  name string, parentheses tricks, assignment — is a PARSE ERROR at
  ingestion, before any geometry exists. There is no string-to-code
  boundary anywhere in the pipeline; the evaluator returns numbers
  only. This is the entire attack surface, and it is closed by
  construction.

1.4 — INSTANTIATION: from recipe to concrete parts
--------------------------------------------------------------------------------

  instantiateRecipe(recipe, seed, overrides):
    1. rng = mulberry32(hash(recipe.id + ':' + seed))     (LAW 6)
    2. Draw each param uniformly in [min, max] (overridable).
    3. Evaluate all expressions bottom-up (foreach expands first).
    4. Emit a concrete part list -> prim calls + a concrete collider
       set + concrete anchors.
  DETERMINISM: recipe + seed -> identical parts, forever. A palm
  placed at seed 4471 is the SAME palm on every regeneration — which
  is what makes the success registry and the failure blacklist
  meaningful for recipe-sourced assets.

1.5 — THE INGESTION WORKFLOW (step by step, in order)
--------------------------------------------------------------------------------

  STEP 1  PARSE + L1 SCHEMA VALIDATION
          Unknown fields rejected; expression grammar enforced;
          budgets checked. Failure -> Clarify round (1.6) with the
          exact offending part/field cited.

  STEP 2  STATIC SAFETY SCAN
          Ink enum compliance (LAW 2), prim registry check, foreach
          bounds, noCollide audit against the 0.3m rule (LAW 4).

  STEP 3  SANDBOX DRY-RUN (3 seeds minimum)
          Instantiate in the existing Three.js sandbox (the macro-
          dreamer's validator infra): NaN/Infinity checks, self-
          intersection of declared colliders, grounded-ness (does the
          base actually touch Y=0 within tolerance?).

  STEP 4  TACTICAL CONTRACT VERIFICATION
          Every DECLARED role is MEASURED:
            traversable -> A* must path through at 1.8m/2.2m invariants
            *_cover -> collider heights must land in 0.8-1.3 / 2.5-3.0
            grapple_anchor -> a ring seat exists with 1.5m clearance
          Dream never trusts the teacher's claims about MATH it can
          verify itself. Claims that fail -> Clarify, not accept.

  STEP 5  REGISTRATION (the permanent memory)
          Appended to .agents/thematic-memory.json:
            recipes: { "palm_tree": { version, provenance,
              confidence: 0.6, uses: 0, failures: 0, ... } }
          Registered as vignette-library fill for matching anchor
          types; registered in the AST node-type registry if the
          recipe declares a set-piece role (BP3).

  STEP 6  TRIAL DEPLOYMENT (earning confidence)
          The paused generation RESUMES using the new asset. Score
          delta vs the map's pre-pause trajectory is tracked.
            +3 successful uses, no validation regressions ->
              confidence 0.9 ("learned" — never asked again)
            any hard failure attributed to the asset ->
              confidence drops, a NEW TeachRequest is auto-filed WITH
              THE FAILURE DATA ATTACHED (1.7)

  STEP 7  (optional, --review mode) HUMAN SIGN-OFF
          Recipes land in .agents/pending-recipes/ as a knowledge
          pull-request: diffable JSON, approve/reject via the existing
          consultant CLI. Default off (trusted-teacher mode); on for
          public/unknown teachers.

1.6 — THE DIALOG PROTOCOL (rounds, clarification, transports)
--------------------------------------------------------------------------------

  ROUND STRUCTURE (bounded):
    TeachRequest -> RecipeResponse -> [ Accept | Clarify | Reject ]
    Clarify includes ONLY what failed, with measurements:
      "Part 'frond' (i=3) places a noCollide wedge intersecting the
       trunk collider at seed 2 by 0.42m. Adjust the radial offset
       expression or declare noCollide on the collision contract."
    Max 2 Clarify rounds; then the ticket parks and the Standin
    Director improvises a cousin-asset stand-in so the RUN survives
    (the knowledge gap is queued, not fatal).

  THE THREE TRANSPORTS (same as the R6 director, extended):
    T1  CLI: `dream:teach resolve <id> --file recipe.json`
    T2  OFFLINE PACKET: generatePromptPacket() gains a teach mode —
        the packet contains the TeachRequest + the recipe cheat-sheet,
        the human pastes it to ANY frontier LLM, pastes back the JSON.
        (Institutionalizes exactly how this document set is produced.)
    T3  API/local model (OpenAI-compatible, low temperature, strict-
        JSON retry x1) — optional, never required.

  THE TEACHER SEAT: a new director persona — THE FIELD GUIDE (a
  nature illustrator who knows how things are built). The Standin
  Director gains one reflex: cousin-substitution (nearest known asset
  by param-space distance) so un-taught themes still generate at
  reduced confidence instead of halting.

1.7 — THE CLOSING LOOP: FAILURES ASK BETTER QUESTIONS
--------------------------------------------------------------------------------

  An asset that fails in the field generates a RICHER second
  TeachRequest than the first: it ships the original recipe, the
  failing seeds, the measured violation (exact clearance/overlap/
  reachability numbers), and the cousin assets that succeeded nearby.
  The teacher's second answer is therefore surgical. Over time the
  recipe corpus converges the way the learning cache already does for
  placements — Dream's knowledge has a survival-of-the-fitted
  dynamic, and every corpse is a lesson.

1.8 — ACCEPTANCE TESTS
--------------------------------------------------------------------------------

  T1  HALT IS DEAD: an unlearned theme generates a stand-in map and
      files a ticket — the run NEVER exits nonzero for knowledge gaps.
  T2  EXPRESSION SAFETY: a corpus of 50 hostile recipes (proto
      access, eval-ish strings, foreach bombs, budget overruns) all
      fail L1/L2 with actionable errors; zero reach the sandbox.
  T3  DETERMINISM: recipe + seed -> identical geometry across 20
      regenerations and both transports.
  T4  CONTRACT HONESTY: a recipe declaring traversable but measuring
      1.6m bore is REJECTED in step 4 with the measured number.
  T5  PERMANENCE: after 3 successful uses, the asset is never
      re-asked (thematic-memory contains the learned entry); field
      failures reopen tickets automatically with failure data.
  T6  RESUME CORRECTNESS: a paused-and-taught run's final map scores
      within noise of an equivalent fully-known run.
