DREAM PHASE 7 — SYSTEM 5: THE COLLISION OCTREE
"Fight Only What's Near" — Brief Item D: Spatial Caching

5.1 — The Problem, In Numbers
--------------------------------------------------------------------------------

Phase 5.5's curvature-aware collision was correct but unpriced: a rich
jungle map bakes roughly 5,000 collision primitives (capsules for trunks
and branches, sweeps for bent limbs, AABBs for rock). A wave with 13
enemies + the player + ~40 live projectiles means:

  BRUTE FORCE:  54 entities x 5,000 primitives = 270,000 broad-phase
                tests PER FRAME. At even 40ns per test that is ~11ms of
                pure collision — the entire frame budget, spent before
                a single enemy thought about flanking.

  CHUNKED:      each entity tests against the ~80-150 primitives in its
                LOCAL chunk. ~54 x 110 = ~6,000 tests = ~0.24ms.
                A 45x reduction — and it SCALES: a map 4x denser costs
                the runtime NOTHING extra, because nobody is standing
                under all of it at once.

The principle: STATIC geometry cost must scale with LOCAL DENSITY, not
MAP SIZE. The octree is how the map forgets about itself.

5.2 — Collision Baking (generation time, src/perf/collision-baker.js)
--------------------------------------------------------------------------------

A new bake pass walks the REALIZED geometry (after instancing resolution,
File 02) and emits primitives into flat typed arrays — one pass, no
objects, directly transferable to a Worker:

JavaScript

  // The StaticCollisionStore: Structure-of-Arrays, transferable buffers.
  const StaticCollisionStore = {
    // stride 7:  ax, ay, az,  bx, by, bz,  flags
    capsules: new Float32Array(capsuleCount * 7),
    // stride 7:  minX, minY, minZ, maxX, maxY, maxZ, flags
    aabbs:    new Float32Array(aabbCount * 7),
    // stride 4:  centerX, centerY, centerZ, radius    (hulls' bounding)
    hullSpheres: new Float32Array(hullCount * 4),

    flags are bitfields:
      BIT 0-1   collision LOD class: 0=FULL, 1=HULL, 2=AABB  (File 03, 3.6)
      BIT 2     grapple_point     (grapple rings feed chain checks)
      BIT 3     climbable
      BIT 4     destructible_foliage (soft cover, Phase 5.5)
      BIT 5     ceiling_surface   (vertical ambushes, Phase 6 drop attacks)

    queries filter by LOD class mask — one branchless AND per primitive.
  };

Instanced archetypes contribute their CACHED collision set transformed
per instance (File 02): 50 willows = 6 capsule SETS, instantiated into
the store with per-instance transforms. The bake is therefore nearly
instant — it is mostly matrix-multiplying cached data.

5.3 — The Loose Octree (src/perf/loose-octree.js)
--------------------------------------------------------------------------------

WHY "LOOSE": a classic octree puts primitives exactly on boundaries, so a
query near a boundary misses neighbors and entities migrating across
seams thrash re-insertions. A LOOSE octree inflates every node's bounds
by 2x its half-size: primitives land in ONE node, queries near seams
still see across, and the tree never re-balances. Static world = build
once = loose is strictly correct here.

ALIGNMENT WITH THE RENDER GRID: the octree's ROOT layer is aligned to the
40m XZ render cells (File 02, 2.3). Each root cell subdivides in Y (and
XZ below half-size) to max depth 5. One spatial language for culling,
instancing, LOD batches, and collision — every system can ask the others
"what's in this cell" and get the same answer.

JavaScript

  // Node layout: flat arrays, no per-node objects (Worker-friendly).
  // nodeChildren: 8 x Uint32 per node (0 = empty leaf)
  // nodeCenter:   3 x Float32 per node
  // nodeHalf:     1 x Float32 per node (loose half = 2.0 x this)
  // nodeSpan:     2 x Uint32 per node -> [start, end) into the
  //               PRIMITIVE INDEX list (primitives sorted by node)

  query(point, radius, lodMask, outList) {
    // outList is a PREALLOCATED, BORROWED array (pool of query results,
    // rotated per frame). Zero allocation per query — house rule.
    // Walks at most depth+1 nodes; each primitive tested once via
    // (flags & lodMask) !== 0.
  }

5.4 — Asynchronous Build (two paths, same output)
--------------------------------------------------------------------------------

PRIMARY PATH — WEB WORKER (src/perf/octree-worker.js):

  main thread                          worker
  -------------                        -------------
  bake store (typed arrays)
       |
  postMessage({ cmd: 'build',
    capsules, aabbs, hullSpheres,
    bounds, maxDepth, looseness },
    [capsules.buffer, aabbs.buffer,    // TRANSFERABLES: zero-copy
     hullSpheres.buffer])  ------------>  build loose octree
                                          sort primitive indices
       <----------- { nodeChildren, nodeCenter, nodeHalf,
                      nodeSpan, order[] } (transferables back)
  apply `order` permutation to store
  attach StaticCollisionStore to scene

The worker also performs the PARITY VALIDATION (5.7) on its side while it
still holds the raw data — validation is free CPU on a thread the player
isn't waiting on... except it IS during load, so validation is capped at
200 samples (below).

FALLBACK PATH — TIME-SLICED: if Workers are unavailable (rare embed
contexts), the same builder runs on the main thread in 2ms slices during
the loading screen (File 08 timeline absorbs it; maps load during a
loading screen anyway — this path matters mostly for Dream's headless 3x
multiplier loops, where Worker throughput is the better lever).

5.5 — Runtime Queries: The BroadPhaseCache (src/perf/broadphase-cache.js)
--------------------------------------------------------------------------------

Entities do not query the tree per frame — they CACHING-BORROW. Each
entity carries a tiny cache record (preallocated at spawn, pooled):

JavaScript

  entity.broadphase = {
    cellKey: -1,             // which root cell the cache was built from
    primitives: null,        // BORROWED reference to a pooled query list
    lastQueryPos: _v,        // preallocated Vector3 (house rule)
    staleness: 0,            // ms since last refresh
  };

  // Per-frame logic (in the entity's physics step, before narrow phase):
  if (entity.movedSince(lastQueryPos) > cellRadius * 0.25
      || entity.crossedRootCell()
      || staleness > 500) {
    query(point, entityRadius + MARGIN, lodMask(entity), borrowedList);
  }
  // MARGIN = 2m buffer zone: queries return primitives slightly beyond
  // reach, so a sprinting entity does not out-run its own cache between
  // refreshes. The LOOSE bounds (5.3) already bias queries across seams.

PLAYER PRIORITY — PREFETCH: the player's cache is REFRESHED eagerly when
the player comes within 20% of any root-cell boundary: the neighbor
cell's primitives are merged into the borrowed list BEFORE the player
crosses. The player is the one entity that must never tunnel through a
seam the frame it arrives. Enemies tolerate one stale frame; the player
is the camera.

5.6 — The Dynamic Entity Grid (moving things live next door)
--------------------------------------------------------------------------------

Enemies, projectiles, and the player are NOT in the octree (re-inserting
movers per frame re-purchases the cost we just removed). Movers live in a
flat uniform XZ grid, 8m cells:

  dynamicGrid.cell(x, z) -> Int32Array of entity ids (pooled, ring-swapped)

  CONSUMERS:
  - Enemy-enemy separation: same + adjacent cells only (13 enemies that
    are 60m apart never hear about each other).
  - GroupTacticsController (Phase 6, God Mode): ENCIRCLE / BAIT_AND_SWITCH
    formation queries hit the grid instead of the roster — O(local).
  - Sound Hunting (God Mode L4): gunshot events enqueue a grid query in
    a radius, waking dormant AI in nearby cells only.
  - Projectile hits: projectiles check the dynamic grid (soft targets)
    AND the borrowed static list (world) each step — both are local.

5.7 — Parity Validation (the audit that keeps the tree honest)
--------------------------------------------------------------------------------

A chunked structure invites the classic bug: collision that works
everywhere except exactly where two cells meet, discovered by a player
falling through the world at the seam. The Step 6.5 gauntlet (File 07)
therefore validates BEFORE export:

  CHECK 1 — RANDOM PARITY: 200 random points; for each, brute-force
  containment vs chunked query must agree 100%.
  CHECK 2 — SEAM PARITY: 50 points FORCED onto root-cell boundaries and
  octree node seams (offset +- 1cm each side). This is where chunking
  bugs live; we test where they live.
  CHECK 3 — TRANSIT PARITY: a simulated bot sprints 200m crossing ~5
  cells; every frame's borrowed list must be a superset of the brute-
  force list for the bot's position (no missing primitive at the moment
  of crossing — this catches buffer-zone/MARGIN math errors).

  FAILURE PROTOCOL: any disagreement triggers a rebuild with looseness
  2.0 -> 2.5 and depth +1, then re-validation (max 2 retries, then the
  map is flagged for the audit-healer's geometry pass — the flaw may be
  genuinely overlapping baked geometry, which is a MAP bug, not a tree
  bug; the report says which).

5.8 — Cost Summary
--------------------------------------------------------------------------------

  METRIC                        BRUTE FORCE      CHUNKED (Phase 7)
  ----------------------------  --------------  -------------------
  Broad-phase tests / frame     270,000          ~6,000
  Collision CPU / frame         ~11ms            ~0.24ms
  Map density impact            linear           ~none (local only)
  Queries allocating garbage    n/a              0 (pooled borrow lists)
  Build time (5k primitives)    n/a              ~40ms (Worker, async)
  Player seam-tunneling risk    n/a              guarded (prefetch 5.5)

INTEGRATION HOOKS
--------------------------------------------------------------------------------
  - File 02: bake consumes cached per-archetype collision sets, matrix-
    transformed per instance; root cells align to render/instancing cells.
  - File 03: LOD class bits in the flags drive per-entity collision LOD
    (player pinned to FULL, File 03, 3.6).
  - File 06: pooled enemy shells carry their preallocated broadphase
    record; the dynamic grid is the GroupTactics backbone; AI throttle
    bands reuse the same 25m/50m distances.
  - File 04: Rung 5 survival mode reduces ALL AI tick rates — the grid's
    per-cell id lists make batch throttling a per-cell flag flip.
  - File 07: parity validation is gauntlet check #4; octree build report
    (depth, looseness, retries) exports with the map.
  - File 08: Worker kickoff at T+2.5s of the load timeline; borrowed
    lists are rotated per frame so tick() never allocates.
