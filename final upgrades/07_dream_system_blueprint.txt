THE ONE-SENTENCE ARCHITECTURE
-----------------------------
  The map is DATA. The engine is an INTERPRETER. The forest is
  your first compiled program — not your last.

Everything you hand-placed in forest_level_code.js — sector centers,
fields, trails, rivers, the treehouse, the skeleton, chains of
grapples — is a RECIPE waiting to be written down. Dream's job is to
read recipes and run the same placement grammar you just exercised
by hand. Nothing in the engine may know the word "forest".

THE FIVE LAYERS (build them in this order)
-------------------------------------------
  L1  Builder Contract      every prefab speaks the same language
  L2  Map Recipe            the map as a JSON document
  L3  The Scaffold          the interpreter that builds maps from L2
  L4  Palettes & Presets    biome skins + scale knobs (pure data)
  L5  The Orchestrator      generates + verifies + critiques recipes

=====================================================================
L1 — THE BUILDER CONTRACT (the grammar's alphabet)
=====================================================================
Every prefab — existing and future — must satisfy ONE signature:

    build(B, x, y, z, options) -> metrics

Contract rules (enforce with a lint, File 09):

  1. SEEDED RANDOMNESS ONLY
     const rng = createRNG(options.seed ?? hash(x, y, z));
     Zero Math.random anywhere. Same seed + same options = byte-
     identical output. This is what makes recipes reproducible and
     verifiable (File 09 hashes geometry).

  2. OPTIONS SCHEMA WITH DEFAULTS
     Every tunable number is a named option with a default that
     lives in the builder — never buried in a call site. The schema
     is DECLARED so Dream can mutate it:
       buildBambooPlantation.schema = {
         count:  { type:'int', min:16, max:48, def:28 },
         radius: { type:'num', min:6,  max:20, def:12 },
         seed:   { type:'int', def:4421 },
         inkCulm:{ type:'ink', def:'GREEN' }
       };
     Declare the schema object NEXT to each builder. It costs 5
     minutes per prefab and it is what turns "a function Dream can
     call" into "a knob Dream can turn".

  3. NO HARDCODED INK
     Every builder receives its palette entries through options
     (with defaults). No builder may import INK directly for its
     colors — the map recipe owns the palette (L4).

  4. DECLARED FOOTPRINT + CLEARANCES
     footprint: [w, h, d] (registry has this — good) plus:
     clearZone: radius that must stay free of other colliders,
     grappleHooks: [{dx, dy, dz, axis}] so the scaffold knows what
     connectivity a prefab provides WITHOUT raycasting it later.

  5. RETURN METRICS, TRUTHFULLY
     Return what was actually built: { culmCount, height } etc.
     The scaffold logs metrics and the verifier compares promises
     vs reality (this is exactly the check that would have caught
     buildTerracedRidge ignoring `dir` — promised 9.5m, built
     somewhere else).

AUDIT YOUR EXISTING LIBRARY AGAINST THIS (scorecard)
  buildGiantGrass ......... fails rule 1 (Math.random) — File 01 F9
  buildTerracedRidge ...... fails rule 5 (lies about direction)
  buildSuspensionBridge ... deprecated alias (File 01 F10)
  buildTreehouse .......... fails rule 2 (steps/hatch magic numbers)
  Everything else ......... close; needs schema declarations.
One afternoon of retrofit makes the whole library Dream-native.

=====================================================================
L3 — THE SCAFFOLD (the interpreter)
=====================================================================
src/map-scaffold.js — buildMapFromRecipe(recipe) does, in order:

  1. resolve scale preset (L4) -> P, PH, corridor/step/headroom laws
  2. lay ground + tint fields + trails (paint first, build later)
  3. water ribbon + banks + crossings
  4. place LANDMARKS first (they own space; everything yields)
  5. for each sector: field-sample interior -> instantiate core +
     props via instantiatePrefab(id, ...) with per-prop seeds
     derived from recipe.seed + stable hash(sectorId, propIndex)
  6. belt props between overlapping fields (File 03 Tech 3)
  7. vertical pass: Tier-1 kit, grapple chains (respect
     grappleHooks from L1 + gap rules from File 04 Rule 4)
  8. perimeter, spawns, snipers, pickups (with clearance rules,
     File 08)
  9. actors + detail pass (litter/shadows by detail-radius rule)
 10. return L + a BUILD REPORT: every prefab, every option, every
     metric, every rule violation (even non-fatal ones).

Rules 4→5 ordering (landmarks before sectors) fixes a class of bug
you already have: the north ridge/skybridge collision (File 01 F4)
is impossible when placement goes through one reservation system —
the ridge reserves its ascent column, the bridge reserves its deck
band, the scaffold refuses overlaps or auto-offsets.

Dream (src/dream-orchestrator.js) wraps the scaffold:
  concept doc (like your forest_concept.md)
    -> generate recipe JSON (schema-validated)
    -> scaffold builds it
    -> verifier runs (File 09)
    -> failures return to generator as critique (exactly like the
       results.md loop you already run with external LLMs — you are
       automating YOUR OWN review process. That is the product.)

=====================================================================
L5 — THE ORCHESTRATOR LOOP (how the masterpiece repeats)
=====================================================================
  1. GENERATE: concept -> recipe (LLM or template + mutation:
     jitter seeds, swap palette, re-roll sector cores from the
     registry by tag query: registry.query('forest','tunnel'))
  2. BUILD: scaffold -> L + build report
  3. VERIFY: full suite (File 09) — hard fails reject, warnings feed
     back as critiques ("grapple chain 'lanterns' gap=11 > preset
     max 10 at ring 4: move or add ring")
  4. GRADE: screenshot 6 canonical angles (auto-fly camera), score
     composition heuristics (skyline variance, silhouette contrast,
     litter density near landmarks)
  5. SHIP or ITERATE: pass -> map joins the rotation; fail -> back
     to 1 with the critique attached.

You already run steps 1/3/5 MANUALLY with external LLMs (that is
literally what results.md is). Dream is just closing the loop.

THE TEST THAT YOU DID IT RIGHT
-----------------------------

zero new engine code (reusing prefabs; new prefabs only for genuinely
new shapes). If you wrote engine code for pirate cove, the grammar
leaked — patch the grammar, not the map.

"I don't want to be different" — no serious studio hardcodes levels
